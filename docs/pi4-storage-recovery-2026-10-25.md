# Pi4 儲存復原驗證（2026-10-25）

Pi4 原先的容量不足、擴容卡住與跨節點掛載阻塞已排除；本機語音設定也已恢復。模型供應端的帳務／使用額度問題另行記錄，不能以磁碟健康或程序可達推論三種引擎目前都能對話。

## 根因與處理範圍

PVC 已申請 32 GiB，但 Longhorn 1.10.2 引擎與檔案系統仍停在 20 GiB。引擎日誌反覆顯示 iSCSI frontend 擴容的 `nsenter` 目標已不存在。這證明引擎持有失效的 namespace 路徑；沒有足夠證據認定先前是哪個主機服務重啟。現象與 [Longhorn #10544](https://github.com/longhorn/longhorn/issues/10544) 相符。

未完成的擴容要求保留了原節點掛載，造成 Pod 排到其他節點時出現 Multi-Attach。處理前確認兩份副本為 RW、建立可用快照，並保存部署設定與七個登入、模型、配對及初始化檔案的校驗值。確認無進行中的對話後停止 Pi4，等待工作負載卸載及 CSI 掛載解除，再使用程序名稱與 UUID 只重建 Pi4 引擎程序。保留 PVC、PV、兩份副本及快照，未重啟共用 instance-manager。

引擎隨後完成 32 GiB 擴容，擴容要求自動消失。Pi4 恢復後，PVC 與容器檔案系統容量均更新。另將原版本 Helm chart 的磁碟申請值同步為 32 GiB；渲染比對確認僅這個 PVC 的容量欄位不同，其他資源完全一致。

## 部署與語音驗證

- 將 Pi4 移到另一節點，確認掛載與兩個容器就緒；再移除 hostname 綁定，重新排程仍正常。這是受控搬移測試，不是突然斷電或節點失聯測試。
- 檔案系統寫入、`fsync` 及讀回比對通過；七個原有關鍵檔案雜湊保持一致，官方 Paseo Web 沿用原配對重新連線。
- 恢復本機聽寫與語音模式後，找出映像缺少 `bzip2`。透過 Debian 簽署的套件索引取得 `bzip2` 1.0.8-5+b1，安裝至持久 HOME，放進既有服務 PATH；未更換容器映像。
- `parakeet-tdt-0.6b-v2-int8` 與 `kokoro-en-v0_19` 模型下載及解壓縮完成。本機 TTS 產生測試音訊，再由 STT 正確辨識回完整測試句，單次約 6.2 秒。這是本機模型合成音訊測試，未驗證實體手機麥克風、瀏覽器音訊權限或中文語音。
- 模型安裝後仍有超過 11 GiB 可用空間；確切量測時間、容量、Pod 重啟及模型對話結果以 [機器可讀證據](evidence/pi4-storage-recovery-2026-10-25.json) 為準。

## 最新模型驗證與限制

後續 `17:33 UTC` 的驗證已確認 Pi 原生 OAuth 路由可以對話，並完成官方 Web 複驗；詳見[帳號恢復進展](pi4-account-recovery-2026-10-25.md)。以下為儲存修復完成時的 gateway／舊帳號測試結果，不能套用到另一個授權來源。

官方 Paseo Web 的兩個既有 Claude gateway 模型均回 HTTP 402 帳務拒絕；Codex 的原授權回使用額度已用盡；Pi 的既有 ChatGPT gateway 模型回 HTTP 429 `usage_limit_reached`。先前成功的兩輪對話屬於當時驗證，不能代表這次仍然通過。最新驗證狀態已更新，失敗的測試 agent 歸檔保留診斷紀錄。

另外透過 SDK 測試 Pi 既有的 `litellm/qwen3-4b-cluster1`，首輪回覆亦未通過，回報 `PROVIDER_TURN_FAILED`，測試 agent 已歸檔。未將此錯誤推定為帳務問題，也未將目錄中可選取的其他模型視為已通過。

帳務／額度需在實際 provider 帳號處理，或改接使用者指定且已授權的可用路由。更換操作端的對話帳號不會自動覆蓋 Pi4 內保存的 provider 登入；本次未代購額度、改帳號或把其他環境的登入檔複製到 Pi4。

本次完成 Pi4 特定儲存故障復原，不代表已完成長期負載、節點失聯、自動備份還原或所有模型的商業驗收。保留的快照仍在同一儲存系統，不能視為異地備份。Longhorn 版本未升級；失效 namespace 的上游缺陷可能在相關主機服務再次變動後重現。未來維護應核對實際容量、擴容狀態及服務對話，而非只看 PVC 申請值或舊驗證標記。
